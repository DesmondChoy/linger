## Error analysis

This section covers one fix chosen by grouping failures across all 16
Scenarios, and its rerun results.

The `failure_diagnoses` of every failed Scene were grouped by shared cause.
The largest group with a structural cause was Librarian boundary inference.
That stage infers how far the reader has read before any book passage is
retrieved.

**The failure.**
- In Douglass, Helen Keller, and Pinocchio, both model attempts inferred the
  correct chapter, but validation rejected them.
- The output contract made the model copy the complete inventory of up to 20
  candidate passage IDs, accounting for each exactly once.
- The model invented, omitted, or repeated IDs, or cited the same passage
  twice as support.
- Boundary inference allows one retry. After the second rejection the reader
  received a generic clarification question.
- Alice Pigeon returned "uncertain" in one call, which was suspected to be a
  way to avoid the costly contract (Beads `linger-ey6i`).

**The fix.**
- The model no longer writes the inventory. The application derives it: every
  supplied candidate outside the listed occurrences is unrelated by definition.
- Repeated support anchors for one passage merge into the first anchor whose
  excerpt matches that passage. They no longer fail validation.
- Checks that guard the grant are unchanged: unknown or repeated occurrence
  IDs, exact source excerpts, memory assessments, and the one-retry budget.
- Code: `normalize_boundary_candidate` in
  [models.py](../src/linger/agents/librarian/models.py), called from
  `BoundaryMemoryValidation.before_output_validate` in
  [agent.py](../src/linger/agents/librarian/agent.py). The
  [boundary-inference skill](../src/linger/agents/librarian/skills/boundary-inference/SKILL.md)
  no longer asks for the inventory.
- Tests: [test_boundary_inventory_repair.py](../tests/test_boundary_inventory_repair.py).
- Offline check: replaying the captured Douglass and Helen Keller outputs
  through the new validator accepts both on the first call.
- Cross-agent impact: Librarian only. The boundary handoff to Muse and
  Provenance keeps its shape.

**Rerun results.** The six Scenarios that run boundary inference were rerun
once each on 16 October 2026 with `openai:gpt-6-luna`, then LLM-reviewed.

## Run policy

- Use [run-scenario](../.agents/skills/run-scenario/SKILL.md) for selection, model
  confirmation, prerequisite checks, execution, and review. Run sequentially
  with the user and retain **one completed, reviewed result per Scenario**.
- Keep legitimate model failures. Propose fixes for confirmed prompt, code, or
  grader defects, then replace the affected result after a fix and rerun. Do not
  repeat a valid run just to obtain a pass. Keep the previous result if a rerun
  is incomplete.
- Keep the 16 Scenarios and approved expectations fixed. Record outdated
  expectations as limitations. After shared code changes, check earlier results
  for impact. Report single-run observations without repeatability claims.
- Keep `openai:gpt-6-luna`: low reasoning by default; medium for Serendipity,
  Muse draft and revision, and Provenance candidate review. Supper club runs one
  repetition (20 recall cases across 3 curation rounds), like every other Scenario.

When sharing results after each run, give separate **Automated** and
**LLM-review** pass and fail totals, and name the Scenes that passed or failed.
Show inconclusive, unreviewed, and incomplete results explicitly.

For every failure, including an automated pass that fails LLM-review, record
a diagnosis in `failure_diagnoses` in that run's `result.json` and explain it to
the user. The summary's **Failures** section opens each failed Scene with its
failure type and flags any failed Scene that still lacks a diagnosis.

- **Failure type.** Use **legitimate model failure** when adequate instructions,
  inputs, and functioning code were available but the model made an error.
  Use **prompt failure** for unclear, contradictory, or incorrect instructions.
  Use **code failure** for implementation, orchestration, validation, or grader
  defects. Use **architectural failure** when each component works as specified
  but the division of roles, handoffs, or checks lets the error through, for
  example when no stage can verify that kind of claim. Use **setup or provider
  failure** for environment, credential, or provider errors. Use
  **inconclusive** when the evidence cannot establish a type. Mark the cause
  `confirmed` or `suspected`.
- **What failed.** Describe the error briefly and say where it appeared.
- **Ground truth.** State the approved expected behaviour and cite the relevant
  expectation or source passage. Show the actual result or decisive excerpt.
- **Root cause.** Explain where the result first diverged from the expectation,
  with supporting trace, prompt, or code evidence. State whether the cause is
  confirmed or suspected. Use **inconclusive** when evidence cannot establish
  the cause, and name the next diagnostic check.
- **Proposed solution.** Recommend a specific change or future model comparison,
  explain why it addresses the cause, and say how to verify it. For legitimate
  model failures, retain the current result and propose improvements for a
  future comparison. Distinguish proposals from fixes already implemented.

## Storage and reporting

Keep two files per Scenario. `summary.md` holds run findings, failure diagnoses,
follow-up decisions, report and slide points, and Logfire links. `result.json`
holds structured outcomes and the original captured evidence. Keep this README
to shared guidance and the status table, linking to each run's summary.

**Automated** means the runner's implemented checks. **LLM-review** means the
coding assistant's assessment against the full request and approved expectations
after the run. It is separate from Linger's runtime agents and human validation.

Use the skill's bundle and report commands to publish at `results/<scenario>/`.
Replace superseded local results and update this table. Preserve original inputs
and grades. For comparisons, save baseline settings and scores in the report
before replacing traces. Local JSON supports extraction; Logfire adds the span
tree and timings. Replacing local results leaves older Logfire experiments intact.
