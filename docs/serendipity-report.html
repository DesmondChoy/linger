Linger · Multi-agent architecture · Role report

Serendipity

The agent that looks for a connection — and is allowed to say no

Linger is a personal reflection companion built from five specialised AI agents. This report explains Serendipity's role, how it chooses a connection, what the other agents receive, and what the evaluation evidence establishes. Implementation reviewed on 19 September 2026.

The connection-discovery path compares candidates across granted sources. The separate memory-recall skill searches only active account memories and can answer from one matching record. Its result returns through Muse, Provenance, and application release checks. See the role reference for both contracts.

1

What Linger is

Linger is a reflection and memory companion. A person writes about something they are reading or thinking about; the system helps them understand why it mattered, preserves that meaning, and later helps them rediscover it.

It is built as five reasoning agents plus one deterministic service. Each agent is a single reusable model configuration that the surrounding application invokes with a narrow, typed task. No agent has a general conversation with the system; each receives exactly the input its current task needs and returns a structured answer.

The design principle that matters most for this report: no agent can act on the world by itself. Ordinary application code — not a model — decides what gets retrieved, what gets stored, and what the reader actually sees.

ComponentWhat it doesCan it write?
MuseHolds the conversation with the reader and drafts every reply. Decides when to ask a specialist for help.No
LibrarianJudges how far the reader has got in a book, and whether retrieved passages actually support an answer.No
SerendipitySearches permitted sources for a tentative connection worth surfacing, and proposes one or declines.No
SculptorProposes tidying of stored memories — merging duplicates, grouping topics — without destroying originals.No
ProvenanceIndependently reviews every drafted reply before anyone sees it, plus emotional-boundary and curation checks.No
Memory & PolicyNot an agent. Deterministic code that authenticates the account and commits approved changes.Yes
2

Why connection-finding is a separate role

Muse could in principle search for connections itself. Separating the job addresses three specific failure modes.

An agent that must reply will always find something. Muse's job is to produce a reply, so an instruction to "look for an interesting connection" biases it toward producing one whether or not the evidence supports it. Serendipity's job is to return a judgment, and a refusal is a valid judgment. Declining costs it nothing, so restraint is cheap.

Searching the open web is a different risk surface from conversation. Reaching a third-party search service means text can leave the system. That deserves its own boundary, its own privacy gate, and its own audit trail — not a branch inside the conversational agent.

Comparison and evidence access need separate checks. Serendipity considers two or three possible connections and selects one. For example, it might select a link between a character hiding a mistake and the reader's earlier reflection about concealing an error at work. The selected connection is a suggestion Muse may use in its reply. Muse receives the full ranked shortlist, but the application attaches and registers only the evidence records cited by the selected candidate. Candidate text remains untrusted and can still influence the draft, so review and release checks remain necessary.

The core design bet

An agent that is permitted to fail is safer than one that is obliged to succeed. Every contract in the rest of this report exists to make declining structurally easy and manufacturing structurally hard.

3

Where Serendipity sits

Serendipity is not part of the conversation. It is reachable only when Muse chooses to call it, and what it returns is raw material for a draft that still has to survive review.

4

What it may and may not decide

The boundary is deliberately lopsided. Serendipity has broad freedom over judgment and none at all over permission. A model can narrow what reaches the reader; it can never widen it.

May decide

Which permitted source to inspect first, memory and web queries, whether evidence supports a connection, whether an optional source expansion is justified, candidate interpretations, their ranking, and whether to decline.

Must preserve

The reader's exact words as the search cue, the requested intent, the presentation mode the application derived, the list of permitted sources, the frozen book revision and chapter ceiling, and every evidence identifier exactly as returned.

May never decide

Who the account holder is, whether a new source may be opened, where the spoiler boundary falls, whether anything is published, whether memory is written, or whether web content may skip review.

Application code fixes the source grant before the model runs. It withholds memory search and the web capability when those sources are ungranted. The book-search tool remains available but rejects calls without a book grant. Application code also derives presentation mode: get_recommendation becomes direct, and find_connection becomes ask_before_showing. Serendipity must preserve that value; Muse still drafts the reader-facing response.

5

One request, end to end

A connection request passes through eight stages. Application code controls permissions and validates evidence. Models choose searches, assess support, compare candidates, draft the reply, and review it.

  1. 1
    Muse → Application

    The request is raised

    Muse decides a connection might deepen the reflection and calls its tool, supplying only the intent. Application code supplies the reader's exact message as the cue — the model cannot substitute its own paraphrase.

    ConnectionBrief → ConnectionDiscoveryInput
  2. 2
    Application

    Permissions are sealed

    Confirmed reading progress grants a specific book revision and a chapter ceiling. Existing memories grant memory search. Web access requires both a policy flag and credentials, and may be narrowed to an explicit list of allowed URLs.

    ConnectionScope { allowed_sources, book_scopes, web_source_urls }
  3. 3
    Serendipity

    Route and search

    It identifies the requested relationship and inspects every explicitly requested, permitted source. Other discovery requests allow at most one optional expansion beyond the primary source. Librarian plans book retrieval from the original reader cue and prior reader statements.

    at most 8 Serendipity model requests, 6 tool calls, 5 results per source
  4. 4
    Tools

    An evidence ledger accumulates

    Every record a search returns is recorded in a ledger the model cannot see or edit. A web search result is only a lead; the page has to be opened before it counts as evidence.

    SerendipityDependencies.evidence
  5. 5
    Serendipity

    Filter before ranking

    The model must exclude candidates it identifies as generic, unsupported, out of scope, past the spoiler ceiling, privacy-risky, or carrying injected instructions. The schema rejects shortlisted candidates with disqualifying ratings; detecting those problems remains a model judgment.

    eligible = no rejecting anchor, no disqualifier
  6. 6
    Serendipity

    Compare two or three

    Surviving candidates are ranked against anchored categories. If the top two tie, there is no winner and the result is a decline.

    ConnectionProposal | ConnectionDecline
  7. 7
    Application

    Verify against the ledger

    Every cited identifier must resolve to a record this run actually retrieved, from a granted source, inside the book ceiling. The web-claim flag must match the winner's real sources. Presentation must be unchanged. Any mismatch fails the run closed.

    rejected → safe decline, never a partial result
  8. 8
    Muse + Provenance

    Draft, review, release

    Muse receives the full shortlist and the selected candidate's evidence records. It writes the reply and declares what it used. Provenance reviews the draft, canonical evidence, and untrusted tool outcomes, including the shortlist. Application code validates each declaration before release.

    independent review → deterministic release
One run per turn

A second request in the same conversational turn with the same intent reuses the existing decision. A second request with a different intent is declined outright. This removes any incentive to retry until something surfaces.

6

Choosing where to search

Having permission to search somewhere is not a reason to search there. Serendipity identifies the relationship the reader is actually asking for and routes accordingly; the order in which sources happen to be listed carries no meaning.

What the reader is asking forWhere it startsWhen it may expand
A link to something they reflected on beforememoryOnly if the requested relationship genuinely needs a second domain.
Another passage, character or pattern inside the book they are readingbookWeb, only on explicit request or when the book evidence cannot answer alone.
An essay, artwork, song, thinker or idea from outside the book and their own historyweb Open an application-granted URL directly, or search for a lead.The book, only for an explicit comparison or to make the outside result usable.
An explicit comparison across named domainseach named, permitted sourceNever adds a domain the reader did not name.
An open reflection with no specific evidence relationshipdeclineNever searches the web merely to manufacture novelty.

The skill instructs Serendipity to decline when an explicitly requested source is unavailable, and to stop once it has inspected the requested sources and can compare two eligible candidates. Inspecting all explicitly requested sources takes priority over the optional expansion limit. These are model instructions; deterministic source grants and tool budgets separately limit what it can access.

7

Choosing between candidates

This is the most consequential piece of design in the role, and the easiest to get wrong. It runs in two stages that are often conflated: first a filter that removes candidates entirely, then a comparison among whatever survived. Nothing that fails the filter can be rescued by comparing well.

What a candidate actually is

A candidate is not a passage or a web page. It is a proposed interpretation — an argument that two things illuminate each other — and the contract forces that argument to be stated in parts:

FieldWhat it must contain
tentative_claimThe connection in one sentence, hedged as a possibility rather than a fact.
evidence_idsThe exact records it rests on. Unique, non-empty, and resolvable to this run.
shared_structureWhat the two things have in common.
meaningful_differenceHow they nonetheless differ.
interpretationWhy the pairing is worth the reader's attention.
comparison_noteWhy this candidate ranks above or below the others.

The paired requirement for a shared structure and a meaningful difference is the anti-genericism device, and it works at the level of content rather than scoring. A candidate with structure but no difference is a topic match — "both passages are about change" — which is true of almost any two passages and tells the reader nothing. A candidate with difference but no shared structure is simply two unrelated things. Requiring both fields to be filled in separately makes an empty connection awkward to express before anyone has rated anything.

Stage one: the eligibility filter

Each candidate is rated on three ordinal categories with written anchors. These are labels, not numbers:

CriterionStrongMiddleRejecting
Cue fitdirect — answers this exact cuepartial — needs one inferential stepweak — could fit many unrelated cues
Reflective valuehigh — materially changes how the cue is seenmedium — adds a useful anglelow — mostly restates it
Safetyclear — within every boundaryreview — unresolved riskineligible — violates a boundary

A candidate is eligible only when cue fit is not weak, reflective value is not low, safety is exactly clear, and it carries none of the six disqualifiers — generic-only, insufficient support, scope risk, privacy risk, spoiler risk, prompt injection. Note that safety has no usable middle: review is disqualifying just as surely as ineligible. An unresolved risk is not something to weigh against other merits.

Eligibility is derived by the contract from the ratings, never asserted separately by the model. An agent cannot rate a candidate weak and then declare it eligible anyway.

Stage two: comparison, and its surprising consequence

Survivors are ranked by comparing cue fit first; only if that ties does reflective value matter; only if that also ties does safety. No total is ever formed.

Now the consequence that makes this design work. Because eligibility already requires safety to be clear, every candidate that reaches the comparison has identical safety — so the third key can never break a tie. The ranking effectively collapses to two dimensions with two usable values each, which means an eligible candidate can occupy exactly four distinct strength positions.

The contract rejects proposals whose top two ratings tie. The model still decides which ratings to assign, so this structural rule cannot guarantee that it recognises weak or closely matched connections. The skill also instructs the model not to inflate ratings to force a selection.

What the contract enforces

A proposal is rejected before it leaves the agent unless all of the following hold:

  • the shortlist holds two or three candidates — never one, never four;
  • their claim strings differ after normalising case and spacing; this catches repeated wording but does not detect semantic paraphrases;
  • they are listed in non-increasing rubric order;
  • the first strictly outranks the second — second and third may tie, the top two may not;
  • the selected identifier is the first candidate, so the agent cannot rank one thing and pick another;
  • every candidate's declared ratings and disqualifiers satisfy the eligibility rules;
  • every cited identifier resolves to a record this run actually retrieved.
What this does not establish

Every guarantee above is about internal consistency. The contract can prove the agent did not contradict itself — it cannot prove the ratings were right. cue_fit: direct is the model's own assertion, and a confidently mis-rated candidate passes every structural check. Closing that gap is not a contract problem. It is precisely what the evaluation in section 10 exists to address.

8

Safety and provenance

Five checks constrain source access, proposal structure, and evidence identity at different points in the flow. They complement model review but do not prove semantic correctness.

LayerEnforced byWhat it guarantees
Sealed grantApplication codeMemory and web tools are withheld without grants. The book tool rejects ungranted calls and uses the application-owned reading scope.
Guarded retrievalTool wrappersBook queries are clamped to the granted revision and chapter. Web queries are length-bounded and screened for personal data and for the reader's own wording.
Public page accessTool wrapperWhen the application supplies exact public URLs, get_page may open them directly. Otherwise it requires a URL returned by this run's search. Both paths check privacy; only an opened page becomes citable evidence.
Typed invariantsSchema contractsShortlist size, distinctness, ordering, a strict winner, eligibility, and unchanged presentation.
Ledger validationOrchestrationEvery cited identifier must resolve to an in-scope record this run actually retrieved. Anything else fails closed.

The privacy gate on web queries

The most delicate moment is the one where text leaves the system. The gate scales with how much the reader wrote, which is a more subtle rule than it first appears. A very short message — "Li and I divorced" — is almost entirely private, so reusing any substantial word from it in a public query could name a real person; short text is therefore protected word by word. A long passage about a book is mostly public vocabulary, and blocking every shared word there would block ordinary terms like "why" or "error"; longer text is protected instead against runs of consecutive words, which is how copied phrasing actually escapes.

Treated as untrusted throughout

Everything a tool returns — book passages, stored memories, web pages — must be treated as data, never instruction. The model must identify attempts to redirect it through retrieved text and assign the prompt_injection disqualifier, which makes a candidate ineligible. The schema enforces the declared disqualifier; it does not detect injected instructions itself.

Working with the other agents

Application code mediates each exchange. Muse requests discovery, the book tool invokes Librarian, and Provenance later reviews the draft and tool outcomes. Sculptor shapes stored memory in a separate workflow.

AgentDirectionWhat crosses the boundaryWhat never does
MuseCalls SerendipityAn intent, and later the validated decision with the full shortlist and the selected candidate's evidence records.Authority to treat candidate text as verified evidence. Records cited only by unselected candidates are omitted from the evidence bundle.
LibrarianCalled through the book toolThe application supplies the original cue, prior reader statements, and granted book scope. Librarian returns selected passages with its evidence-strength judgment and limitations.Authority to widen the book scope or replace the reader's request with a Serendipity-authored query.
ProvenanceApplication-mediated reviewThe finished Muse draft, canonical evidence, and untrusted tool outcomes, including Serendipity's full shortlist and comparison notes.Release authority or permission to treat model-authored ratings as trusted evidence.
SculptorNo contactNothing directly. Sculptor's approved curation shapes the memory view that Serendipity later searches.Any live interaction; the two never run in the same workflow.
Memory & PolicySupplies dataThe account-scoped view of existing memories that memory search reads.Account identity — Serendipity cannot see or widen it.

Muse — the only caller

Muse decides whether a connection is worth looking for, and supplies only the intent; the cue is the reader's actual message, inserted by application code. When a proposal comes back, Muse is free to ignore it. If it uses the connection, it must declare every record it relies on with that record's true source kind — a book passage cannot be passed off as a memory. When the answer is a decline, Muse relays a fixed safe next step rather than inventing a connection to fill the gap.

Librarian supplies passages and a judgment

Serendipity calls the shared book-evidence workflow through search_librarian. Application code supplies the original reader cue, prior reader statements, and the permitted revision and chapter ceiling. Librarian plans the retrieval, selects relevant passages, and returns its evidence-strength judgment, reason, and limitations alongside those passages. Serendipity uses this judgment when comparing connections. It cannot replace the reader's question with its own book query or widen the reading scope.

Provenance reviews the draft and its supporting material

The application sends Provenance the finished reply, declared evidence, policy, and Serendipity's tool result in untrusted_tool_outcomes. That result includes the full shortlist, ratings, and comparison notes. Provenance must assess those claims against the canonical evidence rather than accept the ratings as authority. Its review is a separate model decision, but the shortlist is not hidden from it. Application code retains the final release decision.

Sculptor — adjacent, never concurrent

Sculptor proposes tidying of stored memories in a workflow that runs outside conversation. Its approved results change which memories appear in the retrieval view, so Sculptor shapes what Serendipity can later find — but the two never interact at runtime, and a curation proposal is itself reviewed by Provenance before any change is committed.

10

How it is evaluated

Section 7 ended on a gap: the contracts prove the agent is self-consistent, not that it is right. Evaluation exists to attack that gap — and its central discipline is refusing to let three different claims blur into one.

ClaimIn plain termsEstablished by
Local correctnessGiven this evidence, did Serendipity route, filter, compare and select the way it should?Component evaluation
CoordinationDid the agents hand off correctly, and did the safeguards hold across the whole system?Scenario replay
Reader valueWas the sentence the person actually read worth reading?Human judgement only

The repository treats blurring these as a defect in its own right: a passing component run "must never be aggregated or labeled as an objective pass." The three layers below are built so that each answers one question and visibly declines to answer the others.

Layer one — component evaluation: isolating the decision

What runs. The production Serendipity agent, its selected skill, contracts, and tool adapters. Retrieval dependencies return fixed case evidence, and the book dependency supplies a simulated Librarian judgment. This isolates Serendipity's choices from live retrieval and Librarian's model judgment.

Why fabricate the evidence. This is the key methodological choice. If retrieval quality varied between runs you could never tell a bad decision from bad material — an agent handed three irrelevant passages and declining is behaving correctly, and looks identical to one that declines out of timidity. Fixing the evidence holds everything constant except the thing being measured, so a failure localises to routing, filtering, comparison or selection.

What it is graded on. Eight named behaviours, each phrased as a question about observable conduct rather than about output text:

BehaviourThe question it asks
route_book_relationship_to_librarianWhen the cue is about the book, does it start with the book?
route_external_recommendation_to_webWhen the cue asks for an outside work, does it search the web and open a page before citing it?
expand_source_only_when_justifiedDoes it add another source only when the requested comparison or insufficient support justifies it?
stop_when_primary_source_is_sufficientWhen the first source is enough, does it stop rather than searching on?
select_evidence_with_a_real_semantic_bridgeDoes the winner rest on a specific shared structure and difference, not a topic match?
rank_the_strongest_supported_connectionDoes it pick the uniquely strongest candidate — and decline when the top two tie?
decline_when_no_supported_bridge_existsDoes it decline when the evidence cannot support two eligible candidates?
exclude_ineligible_evidence_before_selectionDoes it remove out-of-scope or untrusted material before comparing?

The loader refuses to run at all if any behaviour has no case, so coverage cannot silently erode as cases are edited.

How the grading avoids self-confirmation. Two details matter. First, routing is checked from the observed run: each case declares which tool operations were allowed, which were required, and which had to come first, and the grader compares that against what the agent actually called — rather than trusting a claim written in the case file. Second, cases are deliberately paired into contrast groups, because a suite where every case expects success cannot detect an agent that always says yes:

Contrast groupOne case expects……its pair expectsWhat the pair isolates
book-specificityproposal a real bridgedecline a generic themeCan it tell a specific connection from a vague one?
winner-clarityproposal a clear winnerdecline tied top twoDoes it decline on a tie rather than pick arbitrarily?

Hard gates and semantic review are kept apart. Hard grading checks roughly a dozen structural properties — the decision type and decline reason, exact evidence identity, rejection of unknown evidence, presentation preservation, web-flag consistency, at least one search before any proposal, expected routing and tool order, request and tool budgets, spoiler scope, the lead-versus-opened-page chain, and the absence of any storage or release tool on the surface. Semantic review separately judges cue fit, reflective value, meaningful difference, tentativeness and forbidden overclaims. A case states its semantic criteria explicitly — for example requiring that a connection "names a meaningful difference between undergoing change and being asked to explain it" while forbidding the claim that "the reader has an identity disorder."

Two deliberate limits on semantic review

A semantic score can never override a failed hard gate — good prose cannot rescue a boundary violation. And the optional automated reviewer uses the same configured model as the agent it is reviewing, so its judgement is explicitly not independent. The default run exposes the rubric for a human instead.

Layer two — scenario replay: testing the handoffs

Scenario replay feeds scripted reader messages through the production chat path, including Muse, Librarian, Serendipity, Provenance, and release validation. Each run uses an isolated account and memory store. Synthetic inputs and expected outcomes are authored before replay; an independent human reviewer must adopt the expected outcomes before they become grading authority.

The runner permits only the supplied public URLs. Web searches remain live when invoked, while get_page returns the adopted page snapshot after the production URL and privacy checks. This makes page contents repeatable, but does not test whether the live page is available or unchanged. The scenario index records adopted Roses and Cross-source scenarios, with neither replayed against the current implementation. Adoption establishes reviewed expectations, not a passing result.

Layer three — production replay: the live path

The narrowest and most realistic layer: one case driven through real chat with real web retrieval. It grades six stages in order and stops at the first failure, marking everything after it as not reached.

#StageWhat a failure here means
1invocationNo discovery event was recorded.
2retrievalSearch observations are missing or record a retrieval failure.
3serendipity_selectionDiscovery failed or the proposal-or-decline decision differs from the expected decision.
4muse_presentationRelease inspection is missing or records a Muse draft or revision failure.
5provenance_reviewThe final Provenance verdict is not pass.
6deterministic_releaseThe release source differs from the expected source or deterministic validation failed.

The first failing stage identifies where to investigate. These checks do not judge the semantic quality of the selected connection or reply, the correctness of Provenance's verdict, or every earlier turn. A blocked response may demonstrate a working safeguard, but a structural failure alone does not establish that the block was correct.

Why the layers cannot substitute for each other

Each layer tests a different set of dependencies. Fixed inputs improve repeatability while leaving the replaced behaviour untested.

LayerCan establishCannot establish
ComponentThe right local decision under controlled evidence; repeatable and cheap.Anything about real retrieval, the other agents, or what the reader saw.
Scenario replayCoordination and safeguards for adopted cases using live searches and saved page contents.General search coverage or the freshness and availability of live page contents.
Production replayThat the live path works end to end for the case that ran.Generality from one case; and structural passes still leave semantics unreviewed.

The repository makes the mapping explicit rather than implied: the behaviour route_external_recommendation_to_web supports the product objective cross-source tentative connection, but that objective additionally requires Muse invocation, real retrieval, Muse presentation, Provenance review, deterministic release and the reader-visible response — none of which the component layer touches.

What none of this establishes

Hard gates establish structural behaviour. The optional model reviewer assesses semantic criteria separately, but neither establishes that a connection helped a real reader reflect. That requires human evaluation. A run can pass its structural checks and still produce an unhelpful suggestion.

Limitations and open work

LimitationWhy it matters
Current live coverage is unestablishedComponent retrieval is simulated. The direct production replay defines one case, and the scenario index describes input validation and replay support without claiming a current live pass. Saved historical results do not establish current search coverage.
Memory component coverage is missingThe memory case remains outside the component baseline in cases/future/. Memory recall and retrieval have deterministic tests and a longitudinal scenario runner; those checks establish different behavior from this component baseline.
Saved results require their recorded contextThe Librarian checkpoint links the retained batch and its known failures. A recorded result applies to its source revision, adopted inputs, and model configuration. The scenario index describes available inputs and replay support.
Reader value remains unvalidatedAn optional model reviewer can assess prose against semantic criteria. Whether the connection helps a person reflect still requires human evaluation.
Images unsupportedThe chat API accepts text. Image input has no retrieval, citation, or release path through Serendipity.

Contract tests check structural boundaries. Historical replay artifacts preserve both exercised paths and failures. Current production behaviour needs fresh replay evidence, and reader usefulness needs human evaluation.
