Linger system design

The Librarian has two flows.

Books are prepared offline, then searched online within strict spoiler boundaries. The Librarian returns exact, traceable evidence to Muse—never a user-facing answer.

Authority ruleThe agent chooses how to search. Application code decides what it may search.
Flow 01 · Offline

Book preprocessing

Turn a verified source book into chapter-aware chunks, stable evidence IDs, and searchable indexes.

Flow 02 · Online

Evidence retrieval

Search only permitted chapters, rank useful passages, and return an evidence bundle to Muse.

    Flow 01 · Deterministic
    
          
    Offline book preprocessing
    
        
    
        
    Runs when a book or a new revision is appended. It contains no LLM reasoning and publishes nothing until validation passes.
    
      
    

      
    
        
    
          Exact input
          
    Authoritative source request
    
          
    Only the source identity is accepted. Book metadata is retrieved and verified.
    
          
    {
  "source_type": "project_gutenberg",
  "gutenberg_id": 11,
  "source_url": "https://www.gutenberg.org/cache/epub/11/pg11.txt"
}
    
        
    
        
    →
    
        
    
          Exact output
          
    Published book version
    
          
    A validated, searchable revision with stable IDs and ready indexes.
    
          
    {
  "status": "published",
  "work_id": "pg11",
  "book_version_id": "pg11-v7be31a2f",
  "section_count": 12,
  "keyword_index_status": "ready",
  "semantic_index_status": "ready"
}
    
        
    
      
    

      
    
        
    
          01
          
    Acquire and verify
    
          
    Download the plain-text file, resolve its URL, store the download time, and calculate the raw SHA-256 hash.
    
          
    English onlyPublic domainPlain text
    
        
    
        
    
          02
          
    Clean and normalize
    
          
    Remove Gutenberg material outside the book body while preserving spelling, punctuation, paragraphs, headings, dialogue, and poems.
    
          
    Stable line endingsNormalized Unicode
    
        
    
        
    
          03
          
    Detect and validate sections
    
          
    Identify chapters or other structural sections, then reject overlaps, empty sections, gaps, and table-of-contents false positives.
    
          
    Fail closed: uncertain chapter detection requires review. The book is not indexed.
    
        
    
        
    
          04
          
    Create chapter-safe chunks
    
          
    Use 450-token targets and 75-token overlap. Prefer paragraph boundaries, and never let a chunk cross a chapter.
    
          
    450 tokens75 overlapExact character range
    
        
    
        
    
          05
          
    Assign evidence identity
    
          
    The ID permanently connects a returned chunk to an exact revision and source location.
    
          
    pg11-v7be31a2f-ch001-ck003

pg11       work
v7be31a2f  revision hash
ch001      chapter
ck003      chunk
    
        
    
        
    
          06
          
    Build both indexes
    
          
    Keyword indexing supports exact terms and names. Semantic indexing stores meaning-based embeddings. Both retain filterable book and chapter metadata.
    
          
    KeywordSemanticModel version recorded
    
        
    
        
    
          07
          
    Publish atomically and remain append-only
    
          
    A version becomes searchable only when source, structure, chunks, evidence IDs, and both indexes pass validation. A revised source creates another version; it never replaces the old one.
    
          
    Old revision  pg11-v7be31a2f-ch001-ck003
New revision  pg11-v91c44d08-ch001-ck003

Both remain independently searchable and verifiable.
    
        
    
      
    
    
    

    
    
      
    
        
    
          
    Flow 02 · Agent + tools
    
          
    Online evidence retrieval
    
        
    
        
    Muse asks for support. Trusted application context defines the allowed area before either search method runs.
    
      
    

      
    
        
    
          Exact input
          
    Muse request + trusted context
    
          
    MUSE REQUEST
{
  "query": "Why does Alice follow the White Rabbit?",
  "book_version_ids": ["pg11-v7be31a2f"],
  "maximum_results": 5
}

SERVER CONTEXT
{
  "account_id": "account-123",
  "chapter": 5,
  "status": "completed"
}
    
        
    
        
    →
    
        
    
          Exact output
          
    Typed evidence result
    
          
    {
  "status": "evidence_found",
  "evidence_strength": "sufficient",
  "strength_reason": "The passage directly supports an answer.",
  "evidence": [
    {
      "evidence_id": "pg11-v7be31a2f-ch001-ck002",
      "text": "Exact source text...",
      "rank": 1
    }
  ]
}
    
        
    
      
    

      
    
        
    
          01
          
    Validate the boundary before search
    
          
    If the user says only “I am on Chapter 5,” Librarian asks whether they started or completed it. No search runs until the answer is clear.
    
          
    
            12345
            6789101112
          
    
          
    Completed 5 → allow 1–5Started 5 → allow 1–4
    
        
    

        
    
          02
          
    Search permitted chunks
    
          
    Keyword and semantic search run over the allowed area only. Later chapters are not searched and are never exposed to a model.
    
          
    Keyword top 10Semantic top 10Semantic ≥ 0.5
    
        
    
        
    
          03
          
    Fuse and deduplicate
    
          
    Combine the two ranked lists without directly comparing incompatible raw scores. The same evidence ID appears only once.
    
          
    {
  "evidence_id": "...ck002",
  "retrieval_methods": ["keyword", "semantic"],
  "keyword_rank": 2,
  "semantic_rank": 1
}
    
        
    

        
    
          04
          
    Reranking and evidence strength are different
    
          
    
            
    
              
    Reranker tool
    
              
    Orders individual candidate chunks by relevance to the exact query. It receives no more than 15 permitted chunks.
    
            
    
            
    
              
    Librarian agent
    
              
    Looks at the best chunks together and judges whether they can answer Muse's request.
    
            
    
          
    
          
    
            
    Sufficient
    The passages directly support an answer.
    
            
    Weak
    Relevant context exists, but it cannot fully answer the request.
    
            
    None
    No useful evidence exists within the allowed material.
    
          
    
        
    

        
    
          05
          
    Weak evidence keeps its context
    
          
    Weak evidence still includes the exact passages and a reason explaining what they cannot establish.
    
          
    {
  "evidence_strength": "weak",
  "strength_reason": "The passage shows the action but not regret.",
  "evidence": [{ "evidence_id": "...ck004", "text": "..." }]
}
    
        
    
        
    
          06
          
    Return only useful evidence
    
          
    Return up to five exact chunks with source metadata, methods, rank, and reranker score. Never pad the result with irrelevant text.
    
          
    Up to 5Exact textResolvable ID
    
        
    
      
    
    
    

    
    
      
    
        
    
          
    Safe behavior
    
          
    Failures never widen access
    
        
    
        
    Optional retrieval features may degrade. Policy and evidence integrity always fail closed.
    
      
    
      
    
        Unclear spoiler boundary
        
    Return clarification_needed and ask whether the current chapter was started or completed. Do not search.
    
      
    
      
    
        Semantic search unavailable
        
    Continue with keyword search, mark the result keyword_only, and include a warning.
    
      
    
      
    
        Reranker unavailable
        
    Use the fused ranking, mark the result fusion_without_reranking, and include a warning.
    
      
    
      
    
        Evidence ID does not resolve
        
    Exclude the broken item. Fail the request if the remaining evidence cannot support the declared strength.
    
      
    
      
    
        No useful evidence
        
    Return no_evidence, an empty evidence list, and the permitted range that was searched.
    
      
    
    
    

    
    
      
    
        
    
          
    Downstream handoff
    
          
    Evidence is not release authority
    
        
    
        
    Librarian's bundle helps Muse draft. Provenance and deterministic checks still decide whether that draft may reach the user.
    
      
    
      
    
        
    01
    Librarian
    Returns exact evidence, strength, reasons, and limitations.
    
        
    02
    Muse
    Drafts a response that separates evidence from interpretation.
    
        
    03
    Provenance
    Reviews the complete response and semantic support.
    
        
    04
    Application checks
    Validates IDs, quotations, source positions, scope, and spoilers before release.
