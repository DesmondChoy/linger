01 · Rationale

Why Serendipity is a separate agent

Muse could search for connections itself. Separating the job addresses three failure modes, and every contract on this page exists to make declining structurally easy and manufacturing structurally hard.

An agent that must reply will always find something. Muse's job is to produce a reply, so an instruction to "look for an interesting connection" biases it toward producing one whether or not the evidence supports it. Serendipity's job is to return a judgment, and a refusal is a valid judgment. Declining costs it nothing, so restraint is cheap.

Searching the open web is a different risk surface from conversation. Reaching a third-party search service means text can leave the system. That deserves its own boundary, its own privacy gate, and its own audit trail — not a branch inside the conversational agent.

Comparison and evidence access need separate checks. Serendipity considers two or three possible connections and selects one — for example, a link between a character hiding a mistake and the reader's earlier reflection about concealing an error at work. Muse receives the full ranked shortlist, but the application attaches and registers only the evidence records cited by the selected candidate. Candidate text remains untrusted and can still influence the draft, so review and release checks remain necessary.

Serendipity is not part of the conversation. It is reachable only when Muse chooses to call it, and what it returns is raw material for a draft that still has to survive review.

02 · Authority

What Serendipity may and may not decide

The model may choose how to search and compare. Trusted application code fixes which sources exist, which book revision is valid, how far the reader has reached, and whether any result can progress toward release.

May decide

The primary source, memory and web queries, whether evidence supports a connection, an optional source expansion, candidate interpretations, shortlist order, and whether to decline.

Must preserve

The active cue, intent, the application-derived presentation mode (get_recommendation → direct; find_connection → ask_before_showing), allowed source list, immutable book revision, chapter ceiling, exact evidence identifiers, and the application-owned search ledger.

May never decide

Account identity, new source access, spoiler authority, public release, durable memory writes, citation trust, or whether web content may bypass Muse, Provenance, and deterministic validation.

03 · Implemented flow

How a connection request flows, end to end

One reusable Serendipity Agent owns the connection-discovery and memory-recall skills. Application code selects the skill before each model run. Each run adds the selected SKILL.md instructions and typed contracts to the agents.serendipity policy in prompt_catalog.yaml. The skill requires inspection of all explicitly requested, permitted sources. Other discovery requests allow at most one optional source expansion.

04 · Source routing

Where Serendipity searches, and when it expands

Ordering in allowed_sources never determines search order. The skill instructs Serendipity to inspect requested sources and decline when one is ungranted. Inspecting all explicitly requested sources takes priority over the limit of one optional expansion. Source grants and tool budgets are enforced separately by application code.

05 · Candidate selection

How candidates are filtered and ranked

The most consequential piece of the design runs in two stages that are often conflated: a filter that removes candidates entirely, then a comparison among whatever survived. Nothing that fails the filter can be rescued by comparing well.

Anchored candidate rubric

Ordinal categories, never a confidence sum.

First keyCue fit
directpartialweak ✕
Second keyReflective value
highmediumlow ✕
Third keySafety
clearreview ✕ineligible ✕

Any disqualifier rejects eligibility: generic-only, insufficient support, scope risk, privacy risk, spoiler risk, or prompt injection. Eligible candidates are ordered lexically; values are never added into a synthetic score.

What a candidate actually is

A candidate is not a passage or a web page. It is a proposed interpretation — an argument that two things illuminate each other — and the contract forces that argument to be stated in parts.

FieldWhat it must contain
tentative_claimThe connection in one sentence, hedged as a possibility rather than a fact.
evidence_idsThe exact records it rests on. Unique, non-empty, and resolvable to this run.
shared_structureWhat the two things have in common.
meaningful_differenceHow they nonetheless differ.
interpretationWhy the pairing is worth the reader's attention.
comparison_noteWhy this candidate ranks above or below the others.

The paired requirement for a shared structure and a meaningful difference is the anti-genericism device, and it works at the level of content rather than scoring. A candidate with structure but no difference is a topic match — "both passages are about change" — which is true of almost any two passages and tells the reader nothing. A candidate with difference but no shared structure is simply two unrelated things. Requiring both fields separately makes an empty connection awkward to express before anyone has rated anything.

Stage one: the eligibility filter

Each candidate is rated on three ordinal categories with written anchors. These are labels, not numbers.

CriterionStrongMiddleRejecting
Cue fitdirect — answers this exact cuepartial — needs one inferential stepweak — could fit many unrelated cues
Reflective valuehigh — materially changes how the cue is seenmedium — adds a useful anglelow — mostly restates it
Safetyclear — within every boundaryreview — unresolved riskineligible — violates a boundary

A candidate is eligible only when cue fit is not weak, reflective value is not low, safety is exactly clear, and it carries none of the six disqualifiers — generic-only, insufficient support, scope risk, privacy risk, spoiler risk, prompt injection. Safety has no usable middle: review is disqualifying just as surely as ineligible. An unresolved risk is not something to weigh against other merits.

Eligibility is derived by the contract from the ratings, never asserted separately by the model. An agent cannot rate a candidate weak and then declare it eligible anyway.

Stage two: ranking the survivors

Survivors are ranked by comparing cue fit first; only if that ties does reflective value matter; only if that also ties does safety. No total is ever formed.

Because eligibility already requires safety to be clear, every candidate that reaches the comparison has identical safety — so the third key can never break a tie. The ranking collapses to two dimensions with two usable values each, which means an eligible candidate can occupy exactly four distinct strength positions.

The contract rejects proposals whose top two ratings tie. The model still decides which ratings to assign, so this structural rule cannot guarantee that it recognises weak or closely matched connections. The skill also instructs the model not to inflate ratings to force a selection.

06 · Safety & provenance

Safety gates and provenance checks

Semantic judgment can narrow a result but cannot widen application authority. The model, tool wrappers, typed contracts, orchestration, and final release validator each enforce a different boundary.

01
Application-owned grantMemory search and Exa tools are withheld without source grants. The book tool remains exposed but rejects calls without a book grant. Every retrieval stays within application-owned scope.
02
Guarded retrievalLibrarian plans book retrieval from the original cue within the granted revision and chapter ceiling. Web queries and page URLs pass privacy checks before access.
03
Exact public page accessWhen scope.web_source_urls is supplied, only those exact URLs may be opened or recorded, and no search lead is required. Otherwise get_page requires a URL returned by this run's search. Unopened results are not evidence.
04
Typed proposal invariantsTwo or three distinct eligible candidates, descending anchors, one clear rank-one winner, and unchanged presentation.
05
Deterministic ledger validationEvery shortlisted ID must resolve to exact in-scope evidence recorded by a permitted search in this run.

The privacy gate on web queries

The most delicate moment is the one where text leaves the system. The gate scales with how much the reader wrote. A very short message — "Li and I divorced" — is almost entirely private, so reusing any substantial word from it in a public query could name a real person; short text is therefore protected word by word. A long passage about a book is mostly public vocabulary, and blocking every shared word there would block ordinary terms like "why" or "error"; longer text is protected instead against runs of consecutive words, which is how copied phrasing actually escapes.

Treated as untrusted throughout

Everything a tool returns — book passages, stored memories, web pages — must be treated as data, never instruction. The model must identify attempts to redirect it through retrieved text and assign the prompt_injection disqualifier, which makes a candidate ineligible. The schema enforces the declared disqualifier; it does not detect injected instructions itself.

07 · Output contract

What Serendipity returns: a proposal or a decline

A proposal includes the full ranked shortlist and identifies one selected connection. Only that candidate's evidence records are attached and registered for release. A decline carries no shortlist or evidence bundle. Candidate text remains untrusted throughout drafting and review.

ConnectionProposal

  • Two or three distinct eligible candidates
  • Selected ID must equal the rank-one candidate
  • Exact evidence IDs and comparison notes
  • Qualitative uncertainty, unchanged presentation, and safe follow-up
  • contains_web_claim exactly when the winner cites web evidence

ConnectionDecline

  • Machine-readable reason such as insufficient evidence, generic theme, no clear winner, unsafe evidence, or unavailable retrieval
  • Application replaces model-authored next steps with one fixed safe message
  • No rejected candidate evidence leaves the boundary
  • A second same-turn request with a different intent also declines; the same intent reuses the turn's decision
  • Counts as a valid outcome—not an agent failure

What the contract enforces

A proposal is rejected before it leaves the agent unless all of the following hold:

  • the shortlist holds two or three candidates — never one, never four;
  • their claim strings differ after normalising case and spacing; this catches repeated wording but does not detect semantic paraphrases;
  • they are listed in non-increasing rubric order;
  • the first strictly outranks the second — second and third may tie, the top two may not;
  • the selected identifier is the first candidate, so the agent cannot rank one thing and pick another;
  • every candidate's declared ratings and disqualifiers satisfy the eligibility rules;
  • every cited identifier resolves to a record this run actually retrieved.
What this does not establish

Every guarantee above is about internal consistency. The contract can prove the agent did not contradict itself — it cannot prove the ratings were right. cue_fit: direct is the model's own assertion, and a confidently mis-rated candidate passes every structural check. Closing that gap is not a contract problem; it is what the evaluation section exists to address.

08 · Memory recall

Memory recall: the second skill

The second assigned skill is deliberately simpler than discovery. For recall_memory, the application grants only active account memories. A completed search_memories call must support every returned evidence ID. One matching record is sufficient. The task has no book or web search, candidate ranking, or permission question. Muse declares the memory evidence and Provenance reviews the answer before release.

09 · Release boundary

What happens after a proposal: review and release

The selected candidate remains untrusted preparation for Muse. Citation and release authority stay outside Serendipity from discovery through display.

Serendipity → Muse

Decision and selected records

Discovery retains its shortlist, ratings, and comparison notes, with exact records for the winner. Recall returns matching memory IDs, exact records, and a bounded relevance note without a shortlist.

Muse → Provenance

Draft and untrusted outcomes

Muse declares the evidence used in its reply. The application supplies Provenance with the draft, canonical records, and untrusted tool outcomes, including Serendipity's full shortlist.

Application → Reader

Fail closed

Selected book records use the canonical evidence map. Memory and web records use a separate registry. Release requires exact active memory or opened-page evidence, visible web citations, and independent review.

10 · Evaluation

How Serendipity is evaluated

The contracts prove the agent is self-consistent, not that it is right. Evaluation exists to attack that gap — and its central discipline is refusing to let three different claims blur into one. A passing component run "must never be aggregated or labeled as an objective pass."

Each layer answers one question and is built to visibly decline to answer the others. The component layer skips Muse, Provenance and release on purpose — it is testing Serendipity's decision and nothing else — which is exactly why its result cannot be read as a system result: whatever a layer holds fixed or skips stays untested until a wider one runs.

LayerClaim it testsThe question it answersCan establishCannot establish
Component evaluationLocal correctnessGiven this evidence, did Serendipity route, filter, compare and select the way it should?The right local decision under controlled evidence; repeatable and cheap.Anything about real retrieval, the other agents, or what the reader saw.
Scenario replayCoordinationDid the agents hand off correctly, and did the safeguards hold across the whole system?Coordination and safeguards for adopted cases, using live searches and saved page contents.General search coverage, or the freshness and availability of live pages.
Production replayCoordination, liveDoes the whole path work with real retrieval, for this case?That the live path works end to end for the case that ran.Generality from one case; a structural pass still leaves semantics unreviewed.
Human reviewReader valueWas the sentence the person actually read worth reading?Whether a connection helped someone reflect.Not automated No recorded review yet.

Layer one: component evaluation of Serendipity alone

What runs. The production Serendipity agent, its selected skill, contracts, and tool adapters. Retrieval dependencies return fixed case evidence, and the book dependency supplies a simulated Librarian judgment. This isolates Serendipity's choices from live retrieval and Librarian's model judgment.

Why fix the evidence. If retrieval quality varied between runs you could never tell a bad decision from bad material — an agent handed three irrelevant passages and declining is behaving correctly, and looks identical to one that declines out of timidity. Fixing the evidence holds everything constant except the thing being measured, so a failure localises to routing, filtering, comparison or selection.

What it is graded on. Eight named behaviours, each phrased as a question about observable conduct rather than output text. The loader refuses to run if any behaviour has no case, so coverage cannot silently erode.

BehaviourThe question it asks
route_book_relationship_to_librarianWhen the cue is about the book, does it start with the book?
route_external_recommendation_to_webWhen the cue asks for an outside work, does it search the web and open a page before citing it?
expand_source_only_when_justifiedDoes it add another source only when the requested comparison or insufficient support justifies it?
stop_when_primary_source_is_sufficientWhen the first source is enough, does it stop rather than searching on?
select_evidence_with_a_real_semantic_bridgeDoes the winner rest on a specific shared structure and difference, not a topic match?
rank_the_strongest_supported_connectionDoes it pick the uniquely strongest candidate — and decline when the top two tie?
decline_when_no_supported_bridge_existsDoes it decline when the evidence cannot support two eligible candidates?
exclude_ineligible_evidence_before_selectionDoes it remove out-of-scope or untrusted material before comparing?

How the grading avoids self-confirmation. Routing is checked from the observed run: each case declares which tool operations were allowed, required, and first, and the grader compares that against what the agent actually called rather than trusting a claim in the case file. Cases are also paired into contrast groups, because a suite where every case expects success cannot detect an agent that always says yes.

Contrast groupOne case expects……its pair expectsWhat the pair isolates
book-specificityproposal a real bridgedecline a generic themeCan it tell a specific connection from a vague one?
winner-clarityproposal a clear winnerdecline tied top twoDoes it decline on a tie rather than pick arbitrarily?

Hard gates and semantic review are kept apart. Hard grading checks roughly a dozen structural properties — decision type and decline reason, exact evidence identity, rejection of unknown evidence, presentation preservation, web-flag consistency, at least one search before any proposal, expected routing and tool order, request and tool budgets, spoiler scope, the lead-versus-opened-page chain, and the absence of any storage or release tool on the surface. Semantic review separately judges cue fit, reflective value, meaningful difference, tentativeness and forbidden overclaims; a case states its semantic criteria explicitly.

Two deliberate limits on semantic review

A semantic score can never override a failed hard gate — good prose cannot rescue a boundary violation. And the optional automated reviewer uses the same configured model as the agent it is reviewing, so its judgement is explicitly not independent. The default run exposes the rubric for a human instead.

Layer two: scenario replay through the full chat path

Scenario replay feeds scripted reader messages through the production chat path, including Muse, Librarian, Serendipity, Provenance, and release validation. Each run uses an isolated account and memory store. Synthetic inputs and expected outcomes are authored before replay; an independent human reviewer must adopt the expected outcomes before they become grading authority.

The runner permits only the supplied public URLs. Web searches remain live when invoked, while get_page returns the adopted page snapshot after the production URL and privacy checks. This makes page contents repeatable, but does not test whether the live page is available or unchanged. The scenario index records adopted Roses and Cross-source scenarios, with neither replayed against the current implementation. Adoption establishes reviewed expectations, not a passing result.

Layer three: production replay with live retrieval

The narrowest and most realistic layer: one case driven through real chat with real web retrieval. It grades six stages in order and stops at the first failure, marking everything after it as not reached.

#StageWhat a failure here means
1invocationNo discovery event was recorded.
2retrievalSearch observations are missing or record a retrieval failure.
3serendipity_selectionDiscovery failed or the proposal-or-decline decision differs from the expected decision.
4muse_presentationRelease inspection is missing or records a Muse draft or revision failure.
5provenance_reviewThe final Provenance verdict is not pass.
6deterministic_releaseThe release source differs from the expected source or deterministic validation failed.

The first failing stage identifies where to investigate. These checks do not judge the semantic quality of the selected connection or reply, the correctness of Provenance's verdict, or every earlier turn. A blocked response may demonstrate a working safeguard, but a structural failure alone does not establish that the block was correct.

The repository makes the mapping explicit rather than implied: the behaviour route_external_recommendation_to_web supports the product objective cross-source tentative connection, but that objective additionally requires Muse invocation, real retrieval, Muse presentation, Provenance review, deterministic release and the reader-visible response — none of which the component layer touches.

What none of this establishes

Hard gates establish structural behaviour. The optional model reviewer assesses semantic criteria separately, but neither establishes that a connection helped a real reader reflect. That requires human evaluation. A run can pass its structural checks and still produce an unhelpful suggestion.
