Serendipity

When Muse asks, Serendipity does one of two jobs. Discovery searches the sources it has been granted and weighs two or three possible connections. If one clearly wins, it proposes that one. Recall looks for what the reader wrote before on the same subject. Either job can decline, and nothing it returns reaches the reader without review.

01 · Why

Why Serendipity is a separate agent

Muse could look for connections itself. Three things go wrong when it does, and each one is a reason to split the work out.

An agent that must reply will find something. Tell Muse to "look for an interesting connection" and it will tend to produce one whether or not the evidence supports it. Serendipity returns a judgment, and "no" is a valid judgment. Declining costs it nothing.

Searching the web is a different risk. A call to a third-party search service sends text outside the system. That needs its own boundary, its own privacy gate and its own audit trail. It should not be a branch inside the conversational agent.

Comparing candidates needs its own checks. Serendipity weighs two or three candidates and picks one. For example, it might link a character hiding a mistake to the reader's earlier note about covering up an error at work. Muse sees the whole shortlist, but only the winner's evidence is attached for release. The shortlist is still untrusted text, so review is still needed.

Serendipity takes no part in the conversation. Muse is the only thing that can call it, and whatever it returns is draft material that still has to pass review.

02 · Authority

What Serendipity may and may not decide

Serendipity chooses how to search and what to propose. Code decides which sources exist, which book revision is in use, how far the reader has read, and whether anything reaches them.

May decide

Which source to search first, what to search for, whether the evidence supports a connection, whether to try one more source, how to interpret candidates, how to order the shortlist, and whether to decline.

Must preserve

The reader's cue, the intent, the presentation mode (direct for a recommendation the reader asked for, ask_before_showing for an unprompted connection), the allowed sources, the book revision and chapter limit, exact evidence IDs, and the search ledger.

May never decide

Who the account belongs to, access to new sources, spoiler rules, release to the reader, writes to memory, whether a citation is trusted, or whether web content can skip Muse, Provenance and validation.

03 · End to end

How a connection request flows, end to end

Code sets the limits, Serendipity works inside them, and then code and a second agent decide what the reader sees. Serendipity cannot widen its own limits at any point. 04 · Expands step 04–05 · discovery

How discovery chooses a connection

Choosing happens in two stages that look like one. The filter comes first and throws candidates out. The ranking comes second and orders what is left. A candidate that fails the filter can't get back in by ranking well.

A candidate is an argument

A candidate is a proposed interpretation, not a passage or a page. The contract, ConnectionCandidate, makes Serendipity state the argument in parts:

FieldWhat it must contain
tentative_claimThe connection in one sentence, phrased as a possibility.
evidence_idsThe exact records it rests on. Unique, non-empty, and traceable to this run.
shared_structureWhat the two things have in common.
meaningful_differenceHow they still differ.
interpretationWhy the pairing is worth the reader's attention.
comparison_noteWhy it ranks above or below the others.

Shared structure and meaningful difference are the guard against generic connections. With structure but no difference you get a topic match ("both passages are about change"), which is true of almost any two passages. With difference but no structure you just have two unrelated things. Asking for both fields separately makes an empty connection hard to write down.

Stage one: the filter

Each candidate is rated on three criteria in its CandidateRubric. The ratings are labels, and they are never added together.

CriterionStrongMiddleRejecting
Cue fitdirect: answers this exact cuepartial: needs one inferential stepweak: could fit many unrelated cues
Reflective valuehigh: changes how the cue is seenmedium: adds a useful anglelow: mostly restates it
Safetyclear: within every boundaryreview: unresolved risk (rejects)ineligible: breaks a boundary

A candidate is eligible only if cue fit isn't weak, reflective value isn't low, safety is exactly clear, and none of six disqualifiers apply: generic-only, insufficient support, scope risk, privacy risk, spoiler risk, prompt injection.

  • Safety has no usable middle. review rejects just as ineligible does. An unresolved risk isn't traded off against other strengths.
  • The contract works out eligibility. The model supplies ratings, and eligibility follows from them. The model can't rate a candidate weak and still call it eligible.

Stage two: ranking the survivors

Survivors are compared on cue fit first. Reflective value matters only if cue fit ties. No total is ever formed.

Every survivor already has safety clear, so safety can never break a tie. That leaves two criteria with two usable values each, which gives four possible positions. If the top two candidates land in the same position, there is no winner and the answer is a decline.

The limit of this design

The contract rejects a proposal whose top two ratings tie. The model still chooses the ratings, though. A model that confidently over-rates a weak candidate passes every structural check. The discovery skill tells it not to inflate ratings to force a winner, but only evaluation can show whether it follows that. See 08.

  • Reflective value doesn't measure anything at the top. The winner was rated high in all 62 proposals, right or wrong. The label marks the agent's pick, and the runner-up gets medium.
  • So the tie rule almost never fires. A decline needs the top two in the same position, and the agent puts its pick one step higher every time. 61 of 62 shortlists had exactly two candidates.

05 · Expands step 04–05 · recall

Memory recall: the second skill

Recall uses the same brief, input and release path as discovery. The difference is the claim. Discovery offers an argument the reader hasn't heard before. Recall returns the reader's own earlier words.

The recall skill is short, about 300 words. Recall makes no argument of its own, so most of the discovery machinery isn't used. The rubric exists to rate an argument, and recall has none to rate.

DiscoveryRecall
SourcesChooses among memories, the book and the web, whichever are granted. A memory becomes one side of a new connection.Memories only. No book scope, so Librarian refuses every call. No web tool.
JudgmentIs this pairing specific, supported and worth reflecting on?Is this the reader's own earlier writing on what the cue asks about?
ShapeA shortlist of 2–3 with one winner.1–3 records, most relevant first. No shortlist, rubric or winner.
ReturnsA proposal or a decline.A recall or a decline. The schema rejects a proposal.

What counts as a match

A record matches only if the reader would recognise it as what they wrote before about this subject. These don't count, however well they fit:

  • shared vocabulary;
  • a general lesson, an analogy or a tactic that would apply anywhere;
  • a similar mood.

Padding the answer with extra records to look fuller is not allowed.

Two ways to decline

no_matching_memory means the search ran and nothing qualified. retrieval_unavailable means the search couldn't run. Muse tells the reader something different in each case, so the distinction matters.

What it may not do

Recall returns a short, length-limited relevance_note saying why the records answer the cue. It may not quote them at length, interpret them, rank them, propose a connection, or draft the reply. Muse writes the reply and Provenance reviews it. Recall has no shortcut to the reader.

How well recall is measured

Four component cases, 19 of 20 runs (23 Sep). Two sets of memories. In the first set, one case the reader's earlier note plainly matches, and the agent recalled it 5 of 5 times. In the other, only a similar mood and some shared vocabulary exist. The agent correctly declined 4 of 5 times and returned a false recall once. Results in 08.

Eight deterministic tests cover the contract. A task gets the result type that matches its intent, and a mismatch is retried. Unknown IDs are rejected. The ID list must have 1–3 unique entries, and the note is length-limited.

06 · Expands the whole run

Safety gates

Serendipity can rule material out. It can't let in anything the application hasn't already allowed. Five checks enforce that, at five points in the run.

01
Grants come from the applicationMemory and web tools are withheld when those sources aren't granted. The book tool is always present but refuses calls without a book grant.
02
Guarded retrievalLibrarian searches from the reader's original cue, within the granted revision and chapter limit. Web queries and URLs pass a privacy check before any request goes out.
03
Only exact pages countIf the application supplies web_source_urls, only those pages can be opened, and no search is needed first. Otherwise get_page only accepts a URL this run's search returned. A search result that was never opened isn't evidence.
04
Typed proposal rulesTwo or three distinct eligible candidates, in descending order, with one clear winner and the presentation mode unchanged.
05
Ledger validationEvery ID on the shortlist must trace to in-scope evidence that a permitted search recorded in this run.

The privacy gate on web queries

The riskiest moment is when text leaves the system, so the gate adjusts to how much the reader wrote.

  • Short messages are protected word by word. "Li and I divorced" is almost all private. Reusing any substantial word from it in a public query could name a real person.
  • Long messages are protected against copied phrases. A long passage about a book is mostly public vocabulary, and blocking every shared word would block words like "why". What leaks in a long message is a run of copied words, so the gate blocks those.
Tool output is data, never instruction

Book passages, memories and web pages are all untrusted. The model has to spot text that tries to redirect it and mark the candidate prompt_injection, which disqualifies it. The schema enforces that flag once it is set. It doesn't detect injections by itself.

07 · Expands steps 06–07

What Serendipity returns, and how it reaches the reader

There are three result types, and the task decides which are allowed. Discovery returns a proposal or a decline. Recall returns a recall or a decline. After that, three more parties stand between Serendipity and the reader.

ConnectionProposal

  • Two or three distinct eligible candidates
  • The selected ID must be the rank-one candidate
  • Exact evidence IDs and comparison notes
  • An uncertainty level, the presentation mode unchanged, and a safe follow-up
  • contains_web_claim is set exactly when the winner cites the web

MemoryRecall

  • One to three evidence IDs, most relevant first
  • Each ID returned by a search_memories call in this run
  • A length-limited relevance_note
  • No shortlist, ranking or rubric
  • Only allowed for a recall_memory task

ConnectionDecline

  • A machine-readable reason, such as insufficient evidence, generic theme, no clear winner, unsafe evidence, or no matching memory
  • Code replaces the model's suggested next step with one fixed, safe message
  • No rejected evidence leaves the boundary
  • A valid outcome, not a failure

Why three types and not one with optional parts. A proposal is valid only with a full shortlist and a clear winner, and a recall never has either. Merging them would mean giving recalls an empty shortlist or loosening the checks on discovery. The application reads the status field to tell them apart.

What the contract enforces on a proposal

These rules live in the models and in validate_serendipity_output.

  • two or three candidates, never one or four;
  • the shortlist as a whole can’t rest on a single record (two readings of the same pair are fine);
  • claim wording that differs after normalising case and spacing (this won't catch a paraphrase);
  • candidates listed from strongest to weakest, with the first strictly ahead of the second;
  • the selected ID is the first candidate, so the agent can't rank one and pick another;
  • ratings and disqualifiers consistent with eligibility;
  • every cited ID traceable to a record this run retrieved.

A second request in the same turn with a different intent is declined. The same intent reuses the turn's first decision.

What the contract can't show

All of the above is internal consistency. The contract proves the agent didn't contradict itself. It can't prove the ratings were right. cue_fit: direct is the model's own claim.

The release boundary

A proposal is not a reply. Muse still has to write one, Provenance still has to review it, and code still has to check every citation.

08 · Evaluation

How Serendipity is evaluated, and what we found

The contracts show Serendipity is consistent. Evaluation asks whether it is right. Results are reported layer by layer and never combined into one score, because a passing component run "must never be aggregated or labeled as an objective pass."

Key findings

  1. Most "agent failures" have been bugs in the evaluation. On 22 Sep, fixing the cases and checker took the original ten cases from 30 to 35 of 50 runs. On 23 Sep it happened again: cases 18, 19 and 32, and the first grading of the look-alike cases, were all test problems found by reading what the agent did. What changed
  2. One real defect remains: it won't turn down a surface match. Case 03 has failed 0 of 5 in every recorded run, under three prompts. The Keller case shows the same weakness on a different book (2 of 5). Cases
  3. Hard gates can't catch overclaiming. The Animal Farm case passes every structural check 5 of 5, but semantic review found it states the book's conclusion as fact. Semantic review
  4. Routing is the least stable step. Grants stop a search reaching a source it was never given. They don't stop it choosing the wrong one of the sources it was given. In one case the same cue went to the book twice in five runs, then to the web four times in the next five. Now case 06 still goes web-first or declines in 2 of 5 runs, and case 09 declined once even though it had enough. Step 03
  5. When one passage is clearly better, it ranks correctly. In cases 45 and 46 the winner rested on the right passage 10 of 10 times, with the runner-up citing weaker evidence. The ranking failures are all about restraint: ties (05, 21) and surface matches (03, 13). Baseline
  6. With look-alikes in the search results, it still picks the right winner. In 19 saved proposals, the winning answer left the look-alike out 18 times. The look-alike usually went into the runner-up as extra support. Baseline
  7. The ratings don't separate good from bad. Every winner, right or wrong, was rated high on reflective value, so the tie rule almost never fires. Cue fit is the one rating with some signal. Ratings in practice
  8. Tie handling is an agent problem, not a fixture problem. Case 05 on Alice passes 3 of 5 on 23 Sep; the same design on Pinocchio (case 21) has passed 1, 2 and 4 of 5 in three runs. When nothing clearly wins, the agent often picks a winner anyway. New cases
  9. Recall works. 28 of 30 runs across six cases on three sets of memories. Both misses were false recalls where only a similar mood existed. Recall run
  10. End to end, the failure is downstream of Serendipity. In scenario replay, Serendipity's stages passed. The failing scene broke at Muse's citations. Scenario replay

Layer one: component evaluation

What runs. The production agent, the skill the application would choose for the case's intent, the real contracts and tool adapters. The tools return fixed evidence for each case, and a simulated Librarian verdict stands in for the live one.

Why the evidence is fixed. If retrieval varied, a bad decision would look the same as bad material. An agent that declines three irrelevant passages is doing the right thing, and it looks identical to one that declines out of timidity. Fixing the evidence means a failure can be traced to routing, filtering, comparison or selection.

How grading works. The harness doesn't read the prose. It checks things it can observe: proposal or decline, the decline reason, which tool ran first, and whether the exact expected IDs were cited. The reason matters because Muse turns it into what the reader is told. Routing is graded against the tools the agent actually called, not against a claim in the case file.

Cases come in contrast pairs. A suite where every case expects "yes" can't catch an agent that always says yes. So a real bridge is paired with a surface match (book-specificity), a clear winner with a tie (winner-clarity), a matching memory with a vague echo (memory-match), and an injection that should be dropped with one that leaves too little to compare (evidence-safety). The loader refuses to run if any behaviour has no case.

Hard gates and semantic review are kept apart. Hard gates check about a dozen structural properties: decision and reason, exact evidence, unknown IDs rejected, presentation preserved, web flag consistent, a search before any proposal, routing and tool order, budgets, spoiler scope, the lead-to-opened-page chain, and that no storage or release tool is exposed. Semantic review separately judges cue fit, reflective value, difference, tentativeness and overclaims, against criteria each case states.

Two limits on semantic review

A semantic score can never override a failed hard gate. Good prose can't rescue a boundary violation. And the automated reviewer uses the same model as the agent, so its verdict isn't independent. By default the rubric is shown for a human to apply instead.

The cases

Forty-six hand-written cases in evals/serendipity/cases/current/, drawn from four public-domain works so no private material is involved. Each case states a reader's question, fixes what the tools return, and states the right answer. A behaviour counts as holding only if every one of its cases passes on every repeat. Each case is also marked Regression (already works, should stay green) or Capability (deliberately hard, expected to start low), and the two are reported separately so easy passes can't hide hard failures.

  • Case 04 accepts either valid decline reason. It went from 0 to 5 of 5. The agent had spotted the injection all along and just labelled it differently.
  • Case 08 lists acceptable evidence instead of required evidence. Both essays answer the cue, so the case grades routing and page-opening, not which of two equal sources was picked.

  • The skill now defines shared_structure. The contract required the field, but the skill had never defined it. The new rule (a shared subject isn't a shared structure) produced correct declines on case 13 but didn't move case 03.

Check the evaluation before tuning the agent

A first attempt at these fixes scored 24 of 50, worse than before. It had three errors of its own. It required candidates to rest on different evidence, which made the agent split a pair that belonged together. And it gave weak verdicts to cases whose evidence was fine, which changed their decline reasons. All three were evaluation bugs, and all three would have looked like agent regressions without a baseline to compare against.

  • Unchanged: the model, and the case files, which are byte-identical.

How to read these numbers

Read the two tiers separately: regression should stay near 100%, capability is expected to start low. Each suite run is one draw from a non-deterministic model, so trust the repeats. A single green run isn't evidence. The bar is every case passing on every repeat, plus semantic review for every proposal, and a hard pass alone isn't enough. Adding cases to a behaviour can only lower its score, which is why cases now cover more than one book. None of these numbers show that a connection helped a real reader. That needs human review.

09 · Status

What works today and what is still open

Serendipity can search books, the reader's memories and the web, with release checks for each. What's missing is evidence: nothing live has been run end to end, no human has reviewed a result, and two judgement calls in the cases are waiting on a person.
