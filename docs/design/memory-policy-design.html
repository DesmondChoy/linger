Deterministic service · Design & progress

Memory & Policy

The sole durable-memory authority derives account scope from trusted request context, enforces capture policy, and owns IDs, storage, and idempotency. Agents may nominate or curate; they never decide identity, consent, or writes.

M·P
Write authorityInterim service
01 · Responsibility

One trusted boundary for every write.

This is not a reasoning role. It is a deterministic service that turns application-owned identity, policy, and reviewed candidates into auditable storage decisions.

May decide

Trusted account scope, whether automatic capture is enabled, whether every deterministic capture rule passes, stable identifiers, filesystem paths, idempotency, atomic commit behavior, and the minimum read projection.

May not accept

Agent-supplied account identity, self-authorised review flags, sensitive content, an unreviewed or substituted candidate, conflicting idempotent retries, or a request that crosses another account’s scope.

02 · Implemented flow

Policy before persistence.

The current service uses an interim one-file-per-capture Markdown record. The adopted target keeps a stable live memory and appends immutable versions and derived records.

Bind and gate the hand-off

Validate source offsets, evidence IDs, event identity, review verdict, and release source. Emotional boundaries and safe declines suppress every write.

05 · Service

Enforce policy

Require capture enabled, review allowance, no sensitive content, and a matching idempotent retry.

save_automatic(context, candidate)
06 · Storage

Commit atomically

Hash the account key, derive an idempotency key, create the record without overwrite, and return created/reused state.

SaveResult { record, created }
