Linger architecture decision · research snapshot 5 August 2026

Pydantic AI or Pi?

How Linger’s five agents would be expressed in each library—and which foundation better protects typed handoffs, narrow tool authority, and the mandatory Provenance release gate.

Recommendation: use Pydantic AI for all five Linger agents.

It fits the Python/FastAPI direction and makes typed outputs, scoped dependencies, testing, and explicit orchestration first-class. Pi is stronger when a custom TypeScript agent loop is itself the product.

Decision map

The non-negotiables

What the framework must make hard to get wrong

Linger is not a swarm. It is a small state machine with five reasoning roles and one deterministic authority boundary. The framework should support that shape without turning policy into prompt prose.

01Narrow tools

Each role sees only its approved capability surface; Provenance never gets write tools.

02Typed handoffs

Pass claims, evidence IDs, confidence, and flags—not unrestricted transcripts.

03Release gate

No Muse draft reaches the user without a Provenance verdict and deterministic checks.

04Server-owned scope

Account identity and write authority come from application dependencies, never model output.

05Testable control

Contract tests must exercise decline, revision limits, tool denial, citation checks, and isolation.

Center of gravity

Same loop, different philosophy

Both libraries can run a model, expose JSON-schema tools, stream events, and switch providers. The practical difference is how much application structure arrives with the loop.

Pydantic AI

A typed application-agent framework for Python.

  • Agent contract: generic dependency and output types; runtime validation with Pydantic.
  • Tools: decorators, toolsets, MCP, preparation hooks, approval wrappers, retries, and validation feedback.
  • Handoffs: documented delegation, programmatic handoff, graph control flow, and shared usage accounting.
  • Operations: OpenTelemetry/Logfire, eval tooling, test models, UI adapters, and four durable-execution integrations.
Best when
Agents are one layer inside a policy-heavy Python service.

Pi Agent Core

A small, stateful TypeScript agent loop with excellent event control.

  • Agent contract: mutable state, messages, model, tools, transform/convert hooks, and a streaming event bus.
  • Tools: TypeBox parameter schemas, parallel/sequential execution, progress updates, pre/post hooks, and abort signals.
  • Handoffs: compose agents yourself or add extensions; subagents are intentionally absent from the default coding harness.
  • Operations: strong provider layer, steering/follow-up queues, optional SQLite sessions, plus a rich coding harness and TUI.
Best when
The agent loop, live UI, or extensible TypeScript harness is itself the product.

Design rule: use programmatic handoffs for safety-relevant transitions. Agent-as-tool delegation is fine for bounded retrieval, but the model should never decide whether its own output bypasses the gate.

How each Linger agent would look

These are deliberately compact architecture sketches, not copy-paste implementations. Both versions preserve the same authority boundary; the visible difference is how much scaffolding the framework supplies.

Pydantic expresses the final contract directly. Pi expresses the same contract through an explicit “emit output” tool plus wrapper code—a valid pattern, but one the team must own.

Pi Agent Coreprovenance.ts
function createProvenance(reviewDeps: ReviewDeps) {
  const reviewTools = bindReadOnlyTools(reviewDeps);
  return new Agent({
    initialState: {
      systemPrompt: PROVENANCE_PROMPT,
      model: reviewModel,
      messages: [],       // context isolation
      tools: [...reviewTools,
        outputTool("emit_verdict", VerdictSchema)],
    },
    streamFn,
    beforeToolCall: ({ toolCall }) =>
      allowOnly(reviewTools, toolCall.name,
                "emit_verdict"),
  });
}

Pi’s explicit mutable state makes isolation understandable, but also easier to accidentally reuse. Prefer a fresh agent factory per review, not reset() plus hope.

async def reflection_turn(req: Turn, deps: AppDeps) -> Reply:
    candidate = (await muse.run(
        req.to_muse_input(), deps=deps.muse,
        usage_limits=TURN_LIMITS,
    )).output

    for attempt in range(2):
        verdict = await review(
            ReviewRequest.from_candidate(candidate),
            deps.review,
        )
        if verdict.decision == "pass":
            checks.verify(candidate, verdict, deps.scope)
            return Reply.release(candidate.text)
        if verdict.decision != "revise" or attempt == 1:
            break
        candidate = (await muse.run(
            RevisionInput(candidate, verdict.findings).model_dump_json(),
            deps=deps.muse,
        )).output

    return Reply.safe_decline()
Pi orchestrationsame policy, more wrapper
async function reflectionTurn(
  req: Turn, deps: AppDeps
): Promise<Reply> {
  let candidate = await runTyped(
    createMuse(deps.muse), req.toMuseInput(),
    MuseCandidateSchema, TURN_BUDGET
  );

  for (let attempt = 0; attempt < 2; attempt++) {
    const verdict = await runTyped(
      createProvenance(deps.review),
      reviewRequest(candidate), VerdictSchema, REVIEW_BUDGET
    );
    if (verdict.decision === "pass") {
      checks.verify(candidate, verdict, deps.scope);
      return Reply.release(candidate.text);
    }
    if (verdict.decision !== "revise" || attempt === 1) break;
    candidate = await runTyped(
      createMuse(deps.muse), revision(candidate, verdict),
      MuseCandidateSchema, REVISION_BUDGET
    );
  }
  return Reply.safeDecline();
}

In both versions, the application—not Muse, not Provenance, and not a “handoff tool”—decides what reaches the browser.

Pros, cons, and traps

Where each choice earns its keep

Pydantic AI: compelling advantages

  • Strongest direct fit for Linger’s typed candidate/verdict/evidence contracts.
  • Dependency injection maps neatly to authenticated scope and service clients.
  • Programmatic handoff and graph options support the plan → act → check → refine flow.
  • Testing, usage limits, observability, MCP, approval, and durability reduce bespoke infrastructure.
  • One Python stack simplifies ownership, CI, deployment, and contract reuse with FastAPI.

Pydantic AI: costs to accept

  • Broader API surface and rapid evolution; pin versions and follow the upgrade guide.
  • Capabilities, graphs, and durable integrations can invite over-engineering. Start with plain async orchestration.
  • Logfire is convenient but optional; keep telemetry portable through OpenTelemetry.
  • Types validate shape, not truth. Provenance and deterministic citation/scope checks remain essential.

Pi: compelling advantages

  • Small, readable loop with unusually clear event sequencing and control.
  • First-rate steering, follow-up queues, tool progress, cancellation, and browser/Node friendliness.
  • The larger coding harness offers TUI, SDK/RPC modes, skills, extensions, sessions, and deep customisation.
  • Good choice if the team standardises on TypeScript and wants to own the policy layer explicitly.

Pi: costs to accept

  • Core deliberately omits first-class subagents, typed final outputs, graph orchestration, and built-in permissions.
  • Preflight hooks can block tools, but OS/process/network isolation still needs a sandbox or container.
  • Session persistence and compaction are useful conversation features, not durable workflow semantics.
  • Using the coding harness for an end-user reflection service may import a coding-agent-shaped abstraction.
  • Adding TypeScript per-agent implementations to a Python backend doubles contracts and operational seams.

Call

Choose one framework; do not mix by agent

The proposal’s “Pi for TypeScript agents; Pydantic AI for Python agents” sounds flexible, but language-per-role is the wrong boundary. These agents exchange small, safety-relevant contracts on nearly every turn. A mixed runtime adds more failure modes than useful autonomy.

9–3matrix edges
Pydantic · Pi

Adopt Pydantic AI, with a deliberately small subset

The recommendation is architectural, not a popularity contest: Linger’s hardest problem is controlled composition around personal data and a mandatory output gate. Pydantic makes that composition more visible in contracts and easier to test in the project’s existing stack.

  1. Build the five roles as global Agent definitions with distinct dependency and output types.
  2. Use plain application-controlled async orchestration first; introduce pydantic-graph only if flow branching becomes genuinely hard to follow.
  3. Use agent-as-tool delegation only for bounded read-only work such as Librarian retrieval.
  4. Keep Provenance as a fresh, restricted run and keep final release in deterministic application code.
  5. Pilot Muse → Provenance plus one Librarian tool; verify contract tests, traces, cost, latency, and cross-account denial before adding the remaining roles.
When would Pi win? If the team commits to an end-to-end TypeScript service and values custom live interaction, event-level loop control, or a reusable agent harness more than first-party typed outputs, testing, and workflow infrastructure. In that case, use pi-agent-core, not the coding CLI, and budget explicitly for output-tool wrappers, schema validation, tracing, evals, budgets, persistence, and sandbox policy.
