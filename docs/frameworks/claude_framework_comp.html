Linger · Stack decision

Pydantic AI vs pi

pydantic-ai 2.23.0 · pi-agent-core 0.83.0
researched 2026-08-05
Prepared for Team 9's framework debate. Code sketches are illustrative against current APIs, not tested implementations.
01 · The short version

Pydantic AI is the closer structural fit; pi is credible if we're TypeScript-native

Our spec is built around typed hand-off contracts, a mandatory Provenance output gate with exactly one bounded revision, deterministic validation, usage limits, tracing, and a 40-case evaluation harness. Pydantic AI has first-class primitives for every one of those: typed output_type, output validators with ModelRetry, UsageLimits, Logfire tracing, and pydantic-evals. With pi, each becomes ordinary code we write and test ourselves — pi deliberately ships only a unified LLM API and an agent loop.

pi remains a credible choice if the team is TypeScript-native: the code is small enough to read end-to-end, the loop is fully inspectable, and nothing it omits is hard to build at prototype scale. What we should not do is the proposal's "Pi for TS agents, Pydantic AI for Python agents" split — it doubles every contract (Pydantic model + TypeBox schema), splits the output gate across runtimes, and buys nothing.

Pydantic AI

Choose when: we want the framework to carry contracts, retries, limits, evals, and tracing — and at least 3 of 5 members are comfortable in Python.

pi

Choose when: the team is strongest in TypeScript, wants a fully transparent loop with no framework magic, and accepts writing the check-and-refine scaffolding (plus evals) by hand.

02 · What Linger's agents demand of a framework

Six things the framework must make easy

From the spec: agents are logical roles invoked with bounded, minimal context; hand-offs carry only claims, evidence identifiers, confidence, and policy flags; Provenance reviews every Muse draft in a context-isolated invocation with no write tools; the deterministic Memory & Policy Service owns all writes and account scope.

Typed hand-off contracts

Every agent returns a structured record (MuseCandidate, EvidenceBundle, Verdict…), validated before the next step consumes it.

Tools with schemas

Corpus search, memory APIs, web search, image analysis — declared with parameter schemas, validated on call.

Scoped delegation

Muse invokes Librarian / Sculptor / Serendipity with a fresh, minimal context — never a shared transcript.

The output gate

Plan → act → check → refine in reviewable application code: Provenance verdict, at most one revision, safe decline on rejection.

Boundaries by construction

No write tools outside Sculptor's request path; account scope injected by the service, never chosen by a model; injection-resistant evidence handling.

Measurement

Usage/cost limits per turn, tracing of decisions and evidence IDs, and a harness for the 40 fixed evaluation cases with hard thresholds.

04 · Agent by agent

The same agent, in both libraries

Start with the shared contracts — both stacks hang everything off them. Then each agent tab shows a side-by-side sketch with notes on what the framework carries vs. what we'd carry.

Shared contracts

the hand-off records from spec §5, as schemas

In Python they are Pydantic models; in TypeScript they are TypeBox schemas (which serialize to plain JSON Schema). Everything downstream hangs off these.

Pydantic AIcontracts.py
class Claim(BaseModel):
    text: str
    evidence_ids: list[str]

class MuseCandidate(BaseModel):
    """Complete draft reply. Never user-facing until reviewed."""
    response_text: str
    claims: list[Claim]
    quotations: list[QuotationRef]
    sensitive_inference: bool
    confidence: float

class Verdict(BaseModel):
    decision: Literal['pass', 'revise', 'reject']
    critique: Critique | None = None
    detected: DetectedItems   # quotes/claims Provenance found itself
One schema, three jobs: the same model is the LLM's output schema, the validation gate, and the type the orchestrator sees. Field descriptions flow into the prompt automatically.
picontracts.ts
import { Type, type Static } from "typebox";

const Claim = Type.Object({
  text: Type.String(),
  evidenceIds: Type.Array(Type.String()),
});

export const MuseCandidate = Type.Object({
  responseText: Type.String(),
  claims: Type.Array(Claim),
  quotations: Type.Array(QuotationRef),
  sensitiveInference: Type.Boolean(),
  confidence: Type.Number(),
});
export type MuseCandidate = Static<typeof MuseCandidate>;

export const Verdict = Type.Object({
  decision: StringEnum(["pass", "revise", "reject"]),
  critique: Type.Optional(Critique),
  detected: DetectedItems,
});
Equivalent power, more ceremony: TypeBox gives compile-time types and runtime validation, but the schema is only enforced where we call Value.Check ourselves — nothing wires it to the model's final answer for us.

Muse

reflection companion · routes work · no write authority · never replies directly

Muse needs: conversation state, image input, tools that delegate to Librarian/Sculptor/Serendipity, a typed MuseCandidate result, and an orchestrating turn function that enforces the Provenance gate with one bounded revision.

Pydantic AImuse.py
@dataclass
class MuseDeps:
    session: SessionState      # account_id, spoiler_boundary, capture opt-in
    corpus: CorpusIndex
    memory_api: ScopedMemoryApi  # pre-scoped by the service, read-only

muse = Agent(
    'openai-responses:gpt-5.2',   # Responses API, per spec §8
    deps_type=MuseDeps,
    output_type=MuseCandidate,    # typed draft — the contract IS the output
    instructions=MUSE_PROMPT,
)

@muse.instructions
def session_context(ctx: RunContext[MuseDeps]) -> str:
    s = ctx.deps.session   # bounded working context only — spec §5.1
    return f'Spoiler boundary: {s.spoiler_boundary}. Topic: {s.topic}.'

@muse.tool
async def ground(ctx: RunContext[MuseDeps], query: str) -> EvidenceBundle:
    """Ask Librarian for cited passages and memories."""
    r = await librarian.run(query,
        deps=LibrarianDeps.from_session(ctx.deps.session),
        usage=ctx.usage)                # delegation: fresh context, shared budget
    return r.output

@muse.tool
async def explore_connection(ctx, cue: str) -> ConnectionProposal | Decline:
    """Hand a cue to Serendipity."""
    return (await serendipity.run(cue, deps=..., usage=ctx.usage)).output

# ── the output gate lives in plain code ────────────────────
async def muse_turn(user_msg, history, deps) -> str:
    result = await muse.run(user_msg, deps=deps, message_history=history,
        usage_limits=UsageLimits(request_limit=8, tool_calls_limit=6))
    verdict = await review(result.output)          # Provenance, isolated
    if verdict.decision == 'revise':               # exactly one revision
        result = await muse.run(revision_prompt(verdict.critique),
            message_history=result.all_messages(), deps=deps)
        verdict = await review(result.output)
    if verdict.decision == 'pass' and quotes_verify(result.output, deps.corpus):
        return result.output.response_text
    return SAFE_DECLINE                             # application-authored
What the framework carries: the typed candidate, schema-validated delegation results, per-turn usage caps, and combined token accounting across Muse + delegates via usage=ctx.usage. The gate itself stays ordinary reviewable code — exactly what the proposal asks for.
pimuse.ts
// structured output by convention: a terminating submit tool
const submitCandidate: AgentTool = {
  name: "submit_candidate",
  description: "Submit your complete draft reply for review.",
  parameters: MuseCandidate,          // TypeBox — validated on call
  execute: async (_id, params) => ({
    content: [{ type: "text", text: "submitted" }],
    details: params,
    terminate: true,                   // stop loop; orchestrator reads details
  }),
};

const ground: AgentTool = {
  name: "ground",
  description: "Ask Librarian for cited passages and memories.",
  parameters: Type.Object({ query: Type.String() }),
  execute: async (_id, { query }, signal) =>
    asToolResult(await runLibrarian(query, session, signal)),
};                                       // runLibrarian = our own sub-loop

const muse = new Agent({
  initialState: {
    systemPrompt: musePrompt(session),   // bounded context, interpolated by us
    model: models.getModel("openai", "gpt-5.2"),
    tools: [ground, exploreConnection, submitCandidate],
    messages: history,
  },
  streamFn: models.streamSimple.bind(models),
});

// ── the output gate: same shape, but we also own extraction,
//    validation, and budget enforcement ─────────────────────
async function museTurn(userMsg: string): Promise<string> {
  await muse.prompt(userMsg);
  const candidate = readSubmitted(muse.state.messages, "submit_candidate");
  if (!Value.Check(MuseCandidate, candidate))
    throw new ContractError("muse");   // no auto-retry — ours to build
  let verdict = await review(candidate);
  if (verdict.decision === "revise") {
    await muse.prompt(revisionPrompt(verdict.critique));
    verdict = await review(readSubmitted(muse.state.messages, "submit_candidate"));
  }
  return verdict.decision === "pass" ? candidate.responseText : SAFE_DECLINE;
}
What we carry: the submit-tool convention, contract validation, "what if the model never calls submit_candidate", retry-on-invalid, and request/token budgets (pi tracks usage per response; enforcement is our loop). None of it is hard — all of it is ours to test.

Librarian

retrieval planner · corpus + scoped memory search · returns cited EvidenceBundle

Librarian picks a strategy (keyword / semantic / hybrid), fuses and reranks, and must respect the spoiler boundary — which is enforced in the tool, not trusted to the prompt.

Pydantic AIlibrarian.py
librarian = Agent(
    'openai-responses:gpt-5.2',
    deps_type=LibrarianDeps,
    output_type=EvidenceBundle,       # ids, excerpts, trust labels
    instructions=LIBRARIAN_PROMPT,
)

@librarian.tool
async def corpus_search(ctx: RunContext[LibrarianDeps],
        query: str,
        strategy: Literal['keyword', 'semantic', 'hybrid']) -> list[Passage]:
    """Search the book corpus with the chosen strategy."""
    return await ctx.deps.corpus.search(
        query, strategy,
        boundary=ctx.deps.spoiler_boundary)   # enforced in code, not prompt

@librarian.tool
async def memory_search(ctx, query: str) -> list[MemoryHit]:
    """Search this account's memories."""
    return await ctx.deps.memory_api.search(query)
    # memory_api was constructed from the authenticated request —
    # the agent cannot name or widen an account (spec §4)

@librarian.tool
def rerank(ctx, candidate_ids: list[str], intent: str) -> list[Ranked]:
    """Rerank fused candidates against the query intent."""
    return ctx.deps.reranker.rank(candidate_ids, intent)
Fit: strategy choice is a typed enum parameter; the EvidenceBundle output feeds Recall@5 / nDCG@5 evals directly. Same eval set runs through pydantic-evals with no extra plumbing.
pilibrarian.ts
// each invocation = a fresh Agent: bounded context by construction
export async function runLibrarian(
  query: string, session: Session, signal?: AbortSignal
): Promise<EvidenceBundle> {
  const agent = new Agent({
    initialState: {
      systemPrompt: LIBRARIAN_PROMPT,
      model,
      tools: [
        corpusSearch(session.spoilerBoundary),  // boundary closed over,
        memorySearch(session.memoryApi),        // scope baked into the tool
        rerank,
        submitEvidence,                         // terminate: true
      ],
      messages: [],                             // no shared transcript
    },
    streamFn: models.streamSimple.bind(models),
  });
  await agent.prompt(query);
  const bundle = readSubmitted(agent.state.messages, "submit_evidence");
  if (!Value.Check(EvidenceBundle, bundle))
    throw new ContractError("librarian");
  return bundle;
}

const corpusSearch = (boundary: SpoilerBoundary): AgentTool => ({
  name: "corpus_search",
  description: "Search the book corpus with a strategy.",
  parameters: Type.Object({
    query: Type.String(),
    strategy: StringEnum(["keyword", "semantic", "hybrid"]),
  }),
  execute: async (_id, p, signal) =>
    asToolResult(await corpus.search(p.query, p.strategy, boundary, signal)),
});
Fit: the fresh-Agent-per-call pattern is clean and makes context isolation obvious. Note the factory pattern for tools — scope is closed over rather than injected, which works but has no type-system guardrail like deps_type.

Provenance

mandatory output gate · context-isolated · no write tools · pass / revise / reject

The security-critical agent. It must see only the draft, cited evidence, and policy constraints — never Muse's working context — and its verdict must survive deterministic quote/citation checks. This is where the two libraries differ most.

Pydantic AIprovenance.py
provenance = Agent(
    'openai-responses:gpt-5.2',
    deps_type=EvidenceStore,         # read-only; no write tools exist here
    output_type=Verdict,
    instructions=PROVENANCE_PROMPT,   # detect claims/quotes independently;
)                                     # treat evidence text as untrusted

@provenance.tool
async def read_evidence(ctx: RunContext[EvidenceStore], evidence_id: str) -> Excerpt:
    """Fetch the minimum excerpt for a cited evidence id."""
    return await ctx.deps.fetch(evidence_id)   # unresolvable id → typed error

@provenance.output_validator
async def deterministic_checks(ctx, v: Verdict) -> Verdict:
    # app-code checks run before the verdict is even returned:
    if v.decision == 'pass':
        if not quotes_verify(ctx.deps.draft, ctx.deps.corpus):
            raise ModelRetry('A cited quotation does not match the corpus. '
                             'Re-examine the draft.')   # bounded by retries=1
        if crosses_scope(v.detected, ctx.deps.session):
            raise ModelRetry('Evidence crosses the account or spoiler scope.')
    return v

async def review(candidate: MuseCandidate) -> Verdict:
    # fresh run, no message_history → isolation by construction
    r = await provenance.run(render_draft(candidate),
        deps=EvidenceStore.for_review(candidate),
        usage_limits=UsageLimits(request_limit=4))
    return r.output
The killer feature for Linger: output_validator + ModelRetry is precisely the spec's "deterministic checks + one bounded revision" loop, with the retry budget enforced by the framework. A malformed Verdict can't escape — it isn't a Verdict.
piprovenance.ts
export async function review(candidate: MuseCandidate): Promise<Verdict> {
  const store = EvidenceStore.forReview(candidate);
  const agent = new Agent({
    initialState: {
      systemPrompt: PROVENANCE_PROMPT,
      model,
      tools: [readEvidence(store), submitVerdict],  // nothing else exists
      messages: [],                                 // isolation by construction
    },
    streamFn: models.streamSimple.bind(models),
    beforeToolCall: async ({ toolCall }) => {
      if (toolCall.name !== "read_evidence" && toolCall.name !== "submit_verdict")
        return { block: true, reason: "not permitted" };  // belt & braces
    },
  });

  await agent.prompt(renderDraft(candidate));
  let verdict = readSubmitted(agent.state.messages, "submit_verdict");

  // deterministic checks + ONE bounded re-ask — hand-rolled loop
  if (verdict?.decision === "pass") {
    const problem = deterministicProblems(candidate, verdict, store);
    if (problem) {
      await agent.prompt(`Check failed: ${problem}. Re-examine the draft.`);
      verdict = readSubmitted(agent.state.messages, "submit_verdict");
      if (deterministicProblems(candidate, verdict, store))
        return { decision: "reject", detected: verdict.detected };
    }
  }
  if (!verdict || !Value.Check(Verdict, verdict))
    return { decision: "reject", detected: emptyDetected() };  // fail closed
  return verdict;
}
Equally isolatable — a fresh Agent with two tools is a genuinely small trusted surface, and beforeToolCall is a nice hard stop. But the retry budget, fail-closed defaults, and "model never submitted" paths are all our own logic. For the gate our whole safety story rests on, every one of those branches needs its own test.

Sculptor

memory curation · only agent that may request writes · service commits

Sculptor proposes structured memories, duplicate links, and groups; the Memory & Policy Service validates and commits with idempotency keys. Both versions keep write authority out of the model's hands the same way: the "write" tool only submits a proposal.

Pydantic AIsculptor.py
sculptor = Agent(
    'openai-responses:gpt-5.2-mini',
    deps_type=SculptorDeps,
    output_type=list[MemoryProposal] | NoCapture,   # declining is typed too
    instructions=SCULPTOR_PROMPT,   # never sensitive traits; preserve originals
)

@sculptor.tool
async def find_related(ctx, text: str) -> list[MemoryHit]:
    """Find candidate duplicates / related memories."""
    return await ctx.deps.memory_api.search(text)

@sculptor.output_validator
def capture_policy(ctx, out):
    if has_sensitive_trait(out):      # excluded from auto-capture, spec §6.3
        raise ModelRetry('Sensitive-trait content must not be captured.')
    return out

# proposals → Memory & Policy Service, which owns the actual write
result = await sculptor.run(turn_summary, deps=deps)
for p in as_list(result.output):
    await policy_service.request_write(p, idempotency_key=key_for(p))
Note the union output: "no capture needed" is a first-class typed outcome, so eval cases for capture precision/recall fall out naturally.
pisculptor.ts
// same submit-tool pattern; two terminating tools model the union
const tools = [
  findRelated(session.memoryApi),
  submitTool("submit_proposals", Type.Array(MemoryProposal)),
  submitTool("submit_no_capture", NoCapture),
];

export async function runSculptor(summary: string, session: Session) {
  const agent = freshAgent(SCULPTOR_PROMPT, tools);
  await agent.prompt(summary);
  const proposals = readSubmitted(agent.state.messages, "submit_proposals") ?? [];
  for (const p of proposals) {
    if (hasSensitiveTrait(p)) continue;      // policy in code, silently drop?
    await policyService.requestWrite(p, keyFor(p));   // service owns writes
  }
}

// bonus: pi's hooks fit the "final capture pass before compaction"
// requirement neatly in a long-lived Muse session:
const muse = new Agent({ ...,
  shouldStopAfterTurn: async ({ context }) => needsCompaction(context.messages),
  transformContext: async (msgs) => compact(msgs),   // prune working context
});
Where pi genuinely shines: transformContext / shouldStopAfterTurn give explicit, inspectable control of compaction — the trigger for Sculptor's bounded final-capture pass. But note the subtle policy question the code hides: dropping a sensitive proposal silently vs. re-asking the model is a decision Pydantic AI's ModelRetry forces you to make explicitly.

Serendipity

connection explorer · web search · must be able to decline

Serendipity searches internal evidence and, when useful, the web — and "no good connection" is a required first-class outcome (≥80% weak-evidence declines). Private memory text must never be copied verbatim into a web query.

Pydantic AIserendipity.py
serendipity = Agent(
    'openai-responses:gpt-5.2',
    deps_type=SerendipityDeps,
    output_type=ConnectionProposal | Decline,   # declining is success
    instructions=SERENDIPITY_PROMPT,
)

@serendipity.tool
async def web_search(ctx, query: str) -> list[WebResult]:
    """General web search for supporting evidence."""
    if leaks_private_memory(query, ctx.deps.memories):   # spec §6.4
        raise ModelRetry('Rephrase without quoting private memory text.')
    return await ctx.deps.search.run(query)

@serendipity.tool
async def internal_evidence(ctx, cue: str) -> EvidenceBundle:
    """Delegate internal retrieval to Librarian."""
    return (await librarian.run(cue, deps=..., usage=ctx.usage)).output
Note: the privacy guard is a ModelRetry, so the model gets one structured chance to reformulate its query — a nicer failure mode than a hard error, and it's logged in the trace.
piserendipity.ts
const webSearch = (memories: MemoryText[]): AgentTool => ({
  name: "web_search",
  description: "General web search for supporting evidence.",
  parameters: Type.Object({ query: Type.String() }),
  execute: async (_id, { query }) => {
    if (leaksPrivateMemory(query, memories))
      throw new Error("Rephrase without quoting private memory text.");
    return asToolResult(await search.run(query));
  },   // thrown errors go back to the model as isError results — same loop
});

const tools = [
  webSearch(session.memories),
  internalEvidence(session),               // wraps runLibrarian()
  submitTool("submit_connection", ConnectionProposal),
  submitTool("submit_decline", Decline),
];
// orchestrator: whichever submit tool fired is the outcome;
// neither fired → treat as decline (fail closed)
Functionally equivalent: pi reports thrown tool errors to the model with isError: true, so self-correction happens — but with no retry budget, a stubborn model can loop; our orchestrator must cap it.
05 · Weighing the two

Pros and cons

Pydantic AI  Python · v2.23.0

For

  • The spec's vocabulary is the framework's vocabulary. Typed hand-off contracts → output_type; bounded revision → ModelRetry with retry budgets; per-turn caps → UsageLimits; delegation with shared accounting → usage=ctx.usage.
  • Validation is unavoidable, not optional. A malformed Verdict or EvidenceBundle never reaches the orchestrator; the model is re-asked automatically within a budget.
  • Evaluation harness mostly exists. pydantic-evals runs dataset-driven cases with custom deterministic evaluators — our 40 versioned cases and thresholds map onto it directly, and Logfire gives the required decision/evidence tracing.
  • Mature and stable: v2, backed by the Pydantic company, supports the OpenAI Responses API named in spec §8, plus MCP and durable execution if we grow into them.
  • Ecosystem gravity: FastAPI backend (already proposed) and eval/data tooling are Python-native; one language across API, agents, and harness.

Against

  • More framework between us and the wire. Retries, output tools, and message shaping happen inside the library; debugging means learning its internals (the graph/node model) when things get weird.
  • Python typing is advisory. The generics (Agent[Deps, Output]) help, but nothing stops an untyped escape hatch the way tsc does.
  • Fast-evolving API surface: large feature set (graphs, deep agents, durable exec) we must consciously not use to keep the prototype simple.

pi  TypeScript · agent-core v0.83.0

For

  • Radical transparency. The loop, events, and state are small enough to read in an afternoon; every safety-relevant branch of our gate is code we wrote and can point to in the report. No hidden prompt shaping.
  • Isolation is trivially auditable: a fresh Agent per invocation with an explicit tool list is the bounded context; beforeToolCall gives a hard allow-list.
  • Best-in-class interactive loop: streaming events, steering, follow-up queues, custom message types (save notices!), and explicit transformContext compaction — genuinely nice for the Muse UX and the pre-compaction Sculptor pass.
  • Serializable everything: Context is plain JSON — session persistence, replay for evals, and cross-provider hand-off come almost free; token + cost tracking is built in.
  • Compile-time types end to end if the web UI is TypeScript anyway.

Against

  • We build the scaffolding ourselves: structured output (submit-tool convention), contract validation, retry budgets, usage limits, fail-closed defaults, delegation plumbing, and the entire eval harness. Each is small; together they are real person-days from a 75-day budget — and each is safety-relevant code we must also test.
  • Pre-1.0 churn: v0.83.0 with frequent releases and a legacy-node20 tag; API breaks are likely inside our project window.
  • The 83k stars are for the coding-agent CLI, not agent-core as a library; docs, examples, and community patterns for our use case (multi-agent product backends) are thin.
  • No observability or evals story — tracing with evidence IDs and the threshold-gated CI harness are entirely bespoke.
06 · Recommendation

Default to Pydantic AI; let team skills be the only override

Default to Pydantic AI for all five agents, with FastAPI serving the web UI and the Memory & Policy Service. The decisive requirements are the ones with hard acceptance numbers: 100% Provenance verdict coverage, 100% rejected-draft suppression, 95% citation precision, and a CI-gated eval harness. Pydantic AI turns most of that enforcement into framework-checked types and validators and gives us pydantic-evals + Logfire for the rest; with pi we'd spend scarce person-days rebuilding and testing that scaffolding instead of building Muse, Librarian, and the corpus.

Choose pi only on a team-skills override: if most members would be materially slower in Python, pi's smaller surface is a fair trade — nothing about Linger requires Pydantic AI. In that case budget explicitly (≈3–5 person-days) for the shared scaffolding: submitTool(), readSubmitted(), contract checks, retry caps, fail-closed defaults, JSONL tracing, and an eval runner.

Either way, pick one stack. The proposal's "Pi for TS agents, PydanticAI for Python agents" hybrid means every contract exists twice (Pydantic model and TypeBox schema, kept in sync by hand), the output gate spans a process boundary, and the eval harness must drive two runtimes. Separation of duties comes from bounded contexts and the deterministic service — not from splitting languages.

  • Decide by: a 1-day spike — implement Provenance's review() in both (it's the smallest agent and the highest-stakes one; the Provenance tab is a starting point) and run it against 5 of the adversarial eval cases.
  • Sensitive to: team language split (5 members, one agent each); whether the UI team wants pi's steering/streaming events; appetite for pre-1.0 dependency churn during the Aug–Oct project window.
  • Not sensitive to: model choice (both speak the OpenAI Responses API and every major provider), the Memory & Policy Service design (plain app code in both), or corpus/index tooling.
